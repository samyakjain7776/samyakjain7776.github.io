Adaptive Vector Search Engine

Faster filtered similarity search through adaptive query planning, PostgreSQL partitioning, and vector indexes.

Sep–Nov 2025Python · PostgreSQL · pgvector · PostGIS

Search that accounts for the filters.

Similarity search becomes a different problem when a query also restricts which records are eligible. Searching a global vector index may suit a broad query, while a narrow geographic or structured filter can make a smaller search space more useful.

I built an adaptive search engine over 515K hotel reviews to choose a retrieval strategy based on filter selectivity: how much of the dataset remains after applying the query’s filters.

A planner for filtered vector search

The system combines PostgreSQL partitioning, pgvector indexes, and PostGIS geospatial filtering. Its planner routes queries between a global HNSW index and parallel searches over partition-local HNSW indexes. HNSW is a graph-based index for approximate nearest-neighbor search.

  1. 01 / QUERYVector + structured filters
  2. 02 / ESTIMATEAssess filter selectivity
  3. 03 / ROUTEGlobal or local indexes
  4. 04 / RETURNRanked matches

For a broad query, the global index searches across the dataset. When filters narrow the eligible records, partition-local indexes offer a way to focus the search. The planner chooses between these paths instead of treating every query alike.

The engine reduced average latency by 22% compared with global approximate nearest-neighbor search while maintaining 98.5% Recall@k on the evaluated workload.

Recall measures how many of the relevant nearest neighbors the approximate search recovers. Reporting it alongside latency makes the speed improvement meaningful; the query mix and filter selectivity still determine where the approach helps.

The decision behind the optimization

A smaller search space can reduce work, but selecting partitions and coordinating searches also has a cost. This project makes that tradeoff part of query planning: use the structure of the query to decide how to search.

It connects database design and retrieval quality, with the planner responsible for finding a useful balance between response time and the neighbors returned.
