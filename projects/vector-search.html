Hybrid Vector Search

Finding similar hotel reviews while respecting location, dates, and ratings—with a choice of global or partition-local search.

Sep–Nov 2025Python · PostgreSQL · pgvector · PostGIS

The closest match still has to meet the filters.

“A quiet hotel near the station” is a similarity search. Add a city, a minimum rating, and a review year, and the search has two jobs: find relevant text and respect the constraints. A global vector index can spend work on neighbors that those filters reject.

This team project explores that problem across 515K European hotel reviews. It combines semantic similarity with structured and geographic filters, and compares a global search against searches over smaller country-and-year partitions.

Choose the search space before searching.

PostgreSQL stores an unpartitioned copy for global search and a partitioned copy with 18 leaves: six countries, each divided into three years. Both use pgvector HNSW indexes; PostGIS handles distance filters.

The router asks PostgreSQL to estimate matching rows with EXPLAIN, without executing the search. Country and year filters identify eligible partitions; estimated selectivity and partition count determine the route.

  • One partition: query its local index directly.
  • Two to ten partitions, with 1–30% estimated selectivity: query them concurrently using a Python thread pool, then merge candidates by cosine similarity.
  • Otherwise: use the global table, including when table statistics are unavailable for a multi-partition query.

These configurable thresholds express a heuristic: narrowing the search space should save enough work to justify coordinating several queries. PostgreSQL still chooses the execution plan within each search.

The course report records average latency of 2,018 ms for hybrid search and 2,603 ms for the global ANN baseline—about 22% lower—with 98.5% recall. These figures describe the report’s experimental workload, rather than a performance guarantee for this implementation.

The experiment compares exact filtered search, global ANN search, and partition-based hybrid search. Medium-selectivity queries offer the clearest opportunity: enough records remain to make exact search expensive, but filters can still remove much of the global search space.

Where the tradeoff gets interesting

More partitions mean more queries, connections, and candidates to merge. A narrow filter can help local search, but partitioning alone does not make every query faster. The router returns its row estimate, chosen strategy, and reason so those decisions can be inspected.

Parallel searches fetch extra candidates before merging the top matches. That can improve approximate retrieval, but does not guarantee exact recall. Stale statistics and correlated filters can also lead to poor routing estimates.

Shared filter construction keeps query semantics consistent across strategies. Each read transaction ends after the query, and a failed partition fails the search rather than quietly returning an incomplete result.
