Multi-tenant RAG
& shared inference

Building a RAG pipeline for multiple tenants and testing whether agentic retrieval improves the answers.

Samyak Jain · Research with Prof. Kexin Rong

System designRetrieval approachesResultsQuestion comparisons

What I set out to build

At Georgia Tech’s D2I Lab, I worked with Prof. Kexin Rong on a question: how can different users or teams share model infrastructure while keeping their documents separate? I treated each user or team as a tenant, with its own retrieval index. The serving design used a shared base model with LoRA adapters for tenant-specific behavior.

The plan was to build the full inference system. With the time available, I focused on implementing the RAG pipeline and comparing two retrieval approaches. I wanted to understand when a single retrieval pass was enough and when an agent could help by searching and reading more documents.

What I found

Agentic retrieval improved PostgreSQL technical QA from 14 to 31 correct answers out of 60. On the paired MuSiQue sample, it answered 33 out of 100 correctly, compared with 34 for the flat baseline. The extra retrieval steps helped on PostgreSQL, but did not improve the overall MuSiQue result.

01

The multi-tenant architecture

In the shared-serving design, each request carries a tenant ID. That ID selects the document index to search and the LoRA adapter to use for generation. The documents stay in separate indexes, while the tenants share the base model and vLLM server.

Keeping retrieval separate

I stored each tenant’s documents and indexes in a separate directory. The retriever receives the tenant ID and loads that tenant’s index before searching.

The current backend also checks tenant IDs and file paths, then passes the same tenant ID to generation. In a deployed service, the API would need to select that ID from the signed-in user’s permissions.

Why I planned to use LoRA

Running a separate model for every tenant would be expensive. LoRA (low-rank adaptation) adds a small set of trainable parameters to a base model, so each tenant could have an adapter while sharing the larger model weights.

The backend now selects a configured adapter name for each request. Training the adapters and measuring shared-serving performance are still next steps. The experiments below test retrieval quality.

02

Flat vs. agentic retrieval

I put both retrievers behind the same interface and used the same generation layer for the final answer. This let me compare how they collected evidence without changing the rest of the pipeline.

Flat baseline

One retrieval pass

  1. QuestionTenant-scoped request
  2. One-shot routerChoose keyword or semantic search
  3. Ranked chunks + context windowExpand around leading hits, then select context
  4. Generate an answerAnswer using the retrieved context

For the benchmark, the flat baseline used one LLM call to choose keyword or semantic search. It also pulled in neighboring chunks for context. It did not revisit the question or plan another search after seeing the results.

Agentic A-RAG

A retrieval loop

  1. QuestionSame tenant scope
  2. Choose one or more toolsKeyword search · semantic search · read chunk
  3. Read the resultsRefine the query and repeat if needed ↺
  4. Return context → generate answerPass the selected chunks to answer generation

I integrated the A-RAG loop with the tenant and generation interfaces. The agent can search, read a chunk, and change its next search based on what it found. I added limits on loops, repeated calls, and tokens to keep it from running indefinitely.

What each retrieval component does

ComponentWhat it doesWhy it matters
Ingestion & chunkingExtract text, preserve source information, and build persistent indexes per tenant.Builds the index ahead of time and keeps a record of where each chunk came from.
Keyword searchMatch literal terms. The A-RAG tool returns chunk IDs and short snippets.Useful for SQL commands, error messages, identifiers, and names.
Semantic searchUse BGE embeddings to find related meaning. The A-RAG tool searches sentence embeddings and maps hits back to chunks.Finds relevant passages when the question and documentation use different words.
read_chunkFetch full text for selected chunk IDs.Lets the agent read details that are missing from a search snippet.
Neighbor expansionAdd surrounding chunks to the baseline’s top results.Helps when an explanation is split between chunks. This is part of the baseline; the agent has three tools.

The agent has three tools, but no fixed number of steps. It can call several tools in one loop. For example, the saved pg-d-006 trace has seven tool calls: two keyword searches, two semantic searches, and three chunk reads. You can see those calls in the question comparison below.

Limits on the agent loop

The final configuration allowed up to 10 loops and 4,000 characters per tool message. Repeated calls increased a penalty score, and reaching the threshold forced the agent to finish. There was also a token budget.

When assembling the final context, I preferred chunks the agent had read. A fallback could also include chunks it had found through search but had not read. This helped avoid returning empty context, though finding a chunk still did not mean the agent would use it correctly.

03

Models and serving changes

Keeping generation separate from retrieval made it easier to change models. These are the main setups recorded in my experiment notes.

01

Llama 3.1 8B

I started with local vLLM serving. The model sometimes invented SQL syntax, skipped steps, or produced invalid tool arguments. I tightened the prompts and added argument handling to deal with those failures.

02

GLM-4.7-Flash AWQ

I moved to this local mixture-of-experts model to try to improve reasoning and tool use. I had to change the parsers, handle responses that contained reasoning but no answer, and separate the serving and application environments.

03

OpenAI backend

I used gpt-5.4-mini for the final paired runs. The generation interface also supported local vLLM, so the pipeline was not tied to OpenAI. I did not run a controlled comparison of the different models.

I also ran into GPU memory contention when the embedding model loaded onto the GPU used by the language model. I moved embeddings to CPU. Keeping the serving environment separate from the application environment helped avoid dependency conflicts when changing models.

04

Results

Both strategies answered the same questions in each paired comparison. The PostgreSQL suite covered SQL behavior and technical workflows. MuSiQue required connecting facts across documents.

I also ran the flat baseline on 500 MuSiQue questions. It scored 34.0% (170/500). A-RAG was evaluated on the paired 100-question sample.

Where A-RAG helped

On PostgreSQL, A-RAG found details that the baseline missed. For the CREATE INDEX … ONLY question, the baseline used documentation about other SQL commands. A-RAG found the passage that explained what ONLY does for index creation.

Where it did not help

On MuSiQue, A-RAG got some questions right that the baseline missed, but also missed questions the baseline answered. In the Messi/Maradona example below, it found the comparison between the players but did not connect it to the signing date.

The time cost

Average retrieval and generation time went from 3.92s to 13.48s on PostgreSQL and 2.04s to 7.29s on paired MuSiQue when switching from flat to A-RAG. The agent averaged about 4.4 loops on PostgreSQL and 4.3 on MuSiQue.

These timings come from the saved runs. I did not run a separate serving-performance benchmark. A-RAG took more time on both datasets, while the accuracy improvement was limited to PostgreSQL.

How the answers were graded

PostgreSQL answers were graded correct, partial, or incorrect. The percentages above count only correct answers. The flat baseline had 35 partial answers and A-RAG had 25. MuSiQue grading used expected-answer checks and guardrails. A response could still receive a correct grade for containing the expected answer even if it sounded uncertain, so I show the saved answers alongside their grades.

The comparison includes differences in chunking and context selection as well as agent planning. These were individual experimental runs, without repeated trials. They measure answer quality in this setup, not the strength of tenant isolation.

What I would build next

I would next connect the retrieval work to the shared-inference experiments I originally planned. The pipeline and saved traces give me a way to check answer quality while changing the serving setup.

That means training tenant adapters, comparing their answers, and measuring memory use and latency when several tenants share one base model. I would also test how scheduling affects requests when they arrive at the same time.
